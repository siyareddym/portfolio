Spotify Track Analysis with SQL (SQLite)

Author

Siya Muthirevulu

Published

August 18, 2026

1. Overview

A 114,000-row dataset of Spotify tracks (genre, artist, popularity, and audio features like danceability, energy, and tempo), queried using SQLite via DB Browser for SQLite — a different engine than the MS Access SQL project elsewhere on this site, deliberately chosen to show window functions and CTEs, which Access doesn’t support natively.

Dataset: Spotify Tracks Dataset, Kaggle

2. Data Quality Check First

Before writing any analytical queries, I checked whether every row represented a distinct track:

SELECT COUNT(*) AS total_rows, COUNT(DISTINCT track_id) AS unique_tracks
FROM tracks;

Result: 114,000 total rows, but only 89,741 unique tracks. The dataset is structured as exactly 114 genres × 1,000 tracks each — and a track that fits multiple genres (e.g., a blues-rock song) simply gets a separate row per genre tag, sharing the same track_id. Confirmed directly:

SELECT track_name, artists, COUNT(DISTINCT track_genre) AS genre_count
FROM tracks
GROUP BY track_id
HAVING genre_count > 1
ORDER BY genre_count DESC
LIMIT 10;
Track Artist Genres
Baby Blue – Remastered 2010 Badfinger 9
Layla Derek & The Dominos 8

This mattered for every query that followed: genre-level questions can use the full table (each genre tag is a legitimate row), but artist- or track-level questions need to deduplicate first, or an artist with a track tagged across several genres would get counted multiple times. Every query below that aggregates by artist or track starts from a unique_tracks CTE for exactly this reason.

3. Top 5 Tracks Per Genre (Window Functions)

WITH ranked AS (
  SELECT track_name, artists, track_genre, popularity,
         RANK() OVER (PARTITION BY track_genre ORDER BY popularity DESC) AS genre_rank
  FROM tracks
)
SELECT * FROM ranked
WHERE genre_rank <= 5
ORDER BY track_genre, genre_rank;

RANK() OVER (PARTITION BY track_genre ORDER BY popularity DESC) restarts the ranking independently within every genre, in a single pass — no per-genre subqueries needed.

Worth noting from the actual output: in the classical genre, four tracks tied at a popularity score of 70 all correctly received the same rank (4), with the next distinct value jumping straight to rank 8 — RANK()’s documented tie behavior (as opposed to DENSE_RANK(), which wouldn’t leave that gap). Confirms the ranking logic is handling ties correctly, not just running without errors.

4. Artists Above Average Popularity (CTE + Deduplication)

WITH unique_tracks AS (
  SELECT DISTINCT track_id, artists, popularity
  FROM tracks
),
artist_avg AS (
  SELECT artists, ROUND(AVG(popularity), 1) AS avg_popularity, COUNT(*) AS track_count
  FROM unique_tracks
  GROUP BY artists
  HAVING track_count >= 3
)
SELECT * FROM artist_avg
WHERE avg_popularity > (SELECT AVG(popularity) FROM unique_tracks)
ORDER BY avg_popularity DESC
LIMIT 15;

Two chained CTEs: unique_tracks removes the genre-duplication found in Section 2, then artist_avg aggregates by artist — restricted to artists with at least 3 tracks, so a single 100-popularity one-hit-wonder doesn’t dominate the list.

Bad Bunny standing out with 26 tracks and an 85.4 average is a good sanity check on the query — it lines up with his real-world status as one of the most-streamed artists globally, not just a query returning syntactically valid but meaningless output.

5. Tempo Tiers vs. Danceability (CASE WHEN Bucketing)

WITH unique_tracks AS (
  SELECT DISTINCT track_id, tempo, danceability, popularity
  FROM tracks
)
SELECT
  CASE
    WHEN tempo < 90 THEN 'Slow'
    WHEN tempo < 130 THEN 'Medium'
    ELSE 'Fast'
  END AS tempo_tier,
  ROUND(AVG(danceability), 3) AS avg_danceability,
  ROUND(AVG(popularity), 1) AS avg_popularity,
  COUNT(*) AS n_tracks
FROM unique_tracks
GROUP BY tempo_tier;
Tempo Tier Avg. Danceability Avg. Popularity Tracks
Slow 0.474 32.5 13,460
Medium 0.615 33.2 43,575
Fast 0.530 33.5 33,426

The actual finding here matters more than the query syntax: danceability moves meaningfully across tempo tiers (0.474 → 0.615 → 0.530 — medium-tempo tracks are the most danceable, not the fastest ones), but popularity barely moves at all (32.5 → 33.2 → 33.5). Tempo has a real relationship with danceability; it has essentially none with how popular a track becomes.

6. Reusable View: Genre Summary

CREATE VIEW genre_summary AS
SELECT track_genre,
       ROUND(AVG(popularity), 1) AS avg_popularity,
       ROUND(AVG(danceability), 3) AS avg_danceability,
       ROUND(AVG(energy), 3) AS avg_energy,
       COUNT(*) AS n_tracks
FROM tracks
GROUP BY track_genre;
SELECT * FROM genre_summary ORDER BY avg_popularity DESC LIMIT 10;
Genre Avg. Popularity Avg. Danceability Avg. Energy
pop-film 59.3 0.597 0.605
k-pop 56.9 0.648 0.676
chill 53.7 0.664 0.427
sad 52.4 0.692 0.462
grunge 49.6 0.457 0.803

A VIEW saves this aggregation permanently in the database — anyone querying it afterward just runs SELECT * FROM genre_summary instead of rewriting the GROUP BY logic from scratch.

7. Skills Demonstrated

  • Window functions: RANK() OVER (PARTITION BY ... ORDER BY ...), including correct handling of tied values
  • Common Table Expressions (CTEs), including chaining two CTEs together in one query
  • Deliberate deduplication before aggregation — recognizing when raw data needs cleaning before a GROUP BY, not just after
  • CASE WHEN bucketing to convert a continuous variable into categorical tiers for comparison
  • Scalar subqueries used as a filter condition (WHERE avg_popularity > (SELECT AVG(...) ...))
  • CREATE VIEW for reusable, persisted aggregations
  • Data-quality verification as a first step, before any analytical query — and using that finding (genre duplication) to directly shape how later queries were written

Data source: Spotify Tracks Dataset, Kaggle.
